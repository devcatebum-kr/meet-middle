# 제품 기획 (2판) — 살아있는 방

> 2026-09-09 작성. 1판(번화가 점수 중심)에서 방향 전환.
> 읽기 좋은 버전: https://claude.ai/code/artifact/c6abeb8e-9715-4ca8-9f83-c259190d4229

## 전제

**이 도구의 기능은 정확한 계산이 아니라 "객관적으로 보이는 것"이다.**

모임 장소를 정할 때 진짜 어려운 건 계산이 아니라 "난 거기 멀어"라고 말하는 일이다.
누군가 고르면 그 사람이 총대를 메고 나머지는 불만을 삼킨다. 도구가 정하면 아무도 총대를 메지 않는다
— 도구가 객관적으로 보이는 한. 그래서 객관성은 알고리즘의 속성이 아니라 **화면의 속성**이다.

## 순서가 뒤집혔다

1판은 "어떤 역을 추천할까"였다. 2판은 **"왜 내 위치를 넣어야 하나"**가 먼저다.
방이 살아 있어야 사람이 넣고, 위치가 모여야 답이 객관적으로 보인다.

### 지금 방은 죽어 있다

```
입력 → 대기(아무것도 없음) → 버튼 → 결과
```

출발지를 넣고 나면 이름 목록만 남는다. 친구를 기다리는 시간이 통째로 빈칸이다.
더 큰 문제는 **내 위치를 넣을 이유가 화면에 없다는 것**. "출발지를 넣어주세요"는 심부름이다.

### 안 넣으면 진짜로 멀어진다

중간지점은 **입력한 사람들의 좌표로만** 계산된다. 그러니 "지금 안 넣으면 이미 넣은 사람들끼리
가까운 곳으로 정해진다"는 협박이 아니라 **알고리즘의 사실 그대로**다.

다만 말로만 하면 약하다. **사람이 들어올 때마다 지점이 눈앞에서 움직여야** 그 문장이 증거를 갖는다.
그래서 "살아있는 방"과 "입력 동기"는 한 몸이고, 같은 배포로 나가야 한다.

### 방이 숨 쉬는 방식

```
1명    지금은 강남 근처            주변 가게 카드
2명    합정 쪽으로 옮겨졌어요       지점이 움직이는 걸 본다
3명    지금 3명 기준 · 홍대입구     안 넣은 사람에겐 이 화면이 곧 경고
확정   대중교통 시간으로 재계산     ODsay 는 여기서만
```

**비용 구조가 맞아떨어진다.** 잠정 지점은 좌표 평균이라 공짜, 주변 가게는 카카오 로컬(한도 넉넉).
비싼 ODsay 30콜/일은 확정 계산에만. 방이 아무리 살아 움직여도 쿼터를 안 건드린다.
폴링(`app.js` `S.poll`)은 이미 돌고 있어 구조 변경도 작다.

## 입력을 부르는 문장 (세 자리에만)

모든 화면에서 재촉하면 소음이 된다.

| 자리 | 문구 |
|---|---|
| 잠정 지점 카드 | 지금 **2명 기준** · 합정 근처 |
| 초대받은 사람 첫 화면 | 아직 내 출발지가 빠져 있어요. 안 넣으면 **지금 2명 기준으로 정해져요** |
| 카톡 초대 메시지 | 범주·수진 넣었어! 너도 넣어야 네 위치가 반영돼 |

**톤 주의**: 위협이 아니라 안내다. 화면이 이미 지점을 움직여 보여주면 문장은 담담해도 작동한다.
세게 쓸수록 도구가 객관적으로 보이지 않는데, 그게 이 서비스의 유일한 자산이다.

## 정직해야 하는 지점

- **확정 후 들어온 사람** — 지금 결과는 계산한 사람 브라우저에만 있다. "넣으면 반영돼요"가 거짓말이 된다. Phase 2에서 해결.
- **잠정 ≠ 확정** — 잠정은 좌표 평균, 확정은 대중교통 minimax. 답이 바뀔 수 있음을 미리 말해야 한다.
- **1명일 때** — "지금은 강남 근처"는 우스워 보인다. 첫 사람에겐 지점 대신 초대에 집중시킨다.

## 단계 (배포 1회씩)

### Phase 1 — 방을 살린다 · 프론트만
- 참여자 좌표 평균으로 **잠정 중간지점** 계속 갱신 (API 호출 0)
- 그 근처 실제 가게를 카드로 노출 (카카오 로컬, 참여자 변동 시에만 호출)
- "지금 N명 기준" 표시 — 상태가 곧 설득
- 초대 배너·카톡 문구에 결과를 한 문장 덧붙임
- 1명일 때는 지점 대신 초대 유도
- **복귀 시 변화 요약** (아래 알림 항목 참고)

### Phase 2 — 결과를 방에 저장한다 · 서버+프론트
- 확정 결과를 방에 저장, 참여자 전원이 같은 화면
- 확정 후 새 참여자가 생기면 "결과가 낡았어요" 표시
- 초대 메시지가 상태 반영 ("이미 정해졌어" vs "아직 모으는 중")

### Phase 3 — 가게까지 좁힌다 · 서버+프론트
**Phase 1에서 가게 카드에 반응이 있었을 때만 만든다.**
- 후보 몇 곳에 참여자별 반응 (참여자 식별은 기존 `pid` 재사용)
- 가장 많이 선택된 곳을 결과로, 근거와 함께

## 알림 — 조사 결과 (2026-09-09)

**웹 푸시는 우리 주 유입 경로에서 이중으로 막힌다.**
- 카톡 인앱 브라우저는 Service Worker 기반 알림 미지원 ([카카오 데브톡](https://devtalk.kakao.com/t/service-worker/27741))
- iOS는 홈 화면 추가(PWA)해야만 웹 푸시. 사파리 탭은 불가

**카카오 자동 발송도 닫혀 있다.** 친구에게 메시지 보내기는 사업자등록증 + 비즈앱 + 검수가 필요하고,
카카오가 명시적으로 *"자동 메시지는 최대한 지양하며, 검수 시 반려될 수 있습니다"* 라고 밝히고 있다
([체크리스트](https://devtalk.kakao.com/t/api-api/116052)). 우리가 원하는 용도가 정확히 막히는 용도다.

**그래서 통제 가능한 레버는 둘뿐이다** — 메시지에 뭐라고 쓸지, "보낼 이유"가 언제 생기게 할지.
실제 발송·수신자·타이밍은 사용자가 정한다. (나쁘지만은 않다. 친구가 보낸 메시지가 열람률이 훨씬 높다.)

**탭 제목 배지(`document.title`)는 데스크톱 한정**이다. 카톡 인앱 브라우저는 뒤로 가면 웹뷰가 닫혀
탭 표시줄 자체가 없다. 주 사용자에겐 거의 무의미하므로 보너스 정도로만.

**대신 어디서나 되는 것: 복귀 시 변화 요약.**
`localStorage`에 방별 "마지막으로 본 상태"(인원수·잠정 지점)를 저장해두고, 다시 열었을 때 차이를 알린다.
카톡 인앱이 창을 닫아 페이지가 새로 로드돼도 저장값이 남아 작동한다.

> "안 본 사이에 2명 들어왔어요. 합정 → 홍대입구로 옮겨졌어요"

## 보류 — 번화가 점수

지하철 승하차 데이터로 번화가를 점수화하는 안. **검증은 했고 지표 자체는 성립했다.**

`저녁 하차 규모 × 심야 승차 비중`으로 27개 역 실측(서울 열린데이터광장 `CardSubwayTime`, 202512):

```
상위   홍대입구 4.52 · 사당 3.30 · 건대입구 2.73 · 잠실 2.71 · 강남 2.27
하위   공덕 0.77 · 선릉 0.58 · 광화문 0.45 · 역삼 0.42 · 시청 0.37
       여의도 0.31 · 가산디지털단지 0.29 · 화곡 0.28 · 길음 0.23
```

오피스가 7곳이 전부 하위로 떨어졌다.

**검증에서 얻은 것 (나중에 필요하면 여기서 다시 시작)**
- 단순 **저녁 하차만 보면 주거지가 1위**가 된다(신림 1위, 사당 2위) — "놀러 온 사람"과 "퇴근해 집에 온 사람"을 구분 못 한다.
- 강남은 오전 하차가 82만이라 저녁/오전 비율로는 오히려 낮게 나온다.
- **판별자는 심야 승차 비중**(23~1시 승차 ÷ 하루 총 승차). 노는 동네는 늦게까지 있다가 타고 나가고, 주거지는 이미 집이라 안 탄다. 홍대 4.7% / 강남 4.2% vs 시청 2.0% / 신림 1.7% / 화곡 0.7%.
- 이 지표가 재는 건 "번화가"가 아니라 **"밤에 술 마시는 동네"** 다. 성수(0.50)·압구정(0.28) 같은 낮 핫플은 안 잡힌다.
- API는 `sample` 키로 역명 필터 조회가 된다(5행 상한): `http://openapi.seoul.go.kr:8088/sample/json/CardSubwayTime/1/5/{YYYYMM}/{호선 또는 공백}/{역명}/`
- 전체 621행을 받아 정적 테이블로 만들려면 무료 키 발급 필요(data.seoul.go.kr).

**접는 이유는 정확도가 아니라 필요 이상으로 정교해서다.** 서울 한정, 월간 집계(요일 구분 불가),
정적 테이블 갱신 부담. 그런데 필요한 정밀도는 "후보 3곳 중 하나는 다양성 있게" 수준이다.
무엇보다 **실제 가게를 계속 보여주면 점수가 필요 없다** — 사용자가 직접 판단한다.

## 아직 안 정한 것

- **가게를 보여주는 목적** — 대기 시간 채우기인지, 실제로 "어디서 먹을지" 정하려는 것인지.
  일단 전자로 가정하고 Phase 1을 만들고, 반응이 있으면 후자로 확장.
- **잠정 지점을 얼마나 자주 바꿀지** — 매번 움직이면 산만하지만, 그 움직임이 곧 설득이라 얌전하면 효과가 없다. 만들어 보고 조절.
- **앱 전환** — 검토했으나 접었다. 설치는 우리 유일한 해자(무설치 초대 루프)를 죽인다.
  위밋플레이스가 그 길에서 멈췄고, 더치 리뷰에서 "친구들 회원가입 안 해도 돼서 편하다"가 유용 표 상위다.
  재검토 신호는 **같은 사람이 방을 여러 번 만드는 게 보일 때**(반복 사용자의 존재).
